# WavyOS: краткий decision memo по реализации аватара

Цель: выбрать наиболее рациональный вариант визуального аватара для текущей стадии проекта.

## 1. Контекст

WavyOS сейчас — это voice-first desktop assistant для Windows с безопасной архитектурой command router:

- STT
- LLM-нормализация
- выбор команды из белого списка
- валидация аргументов
- локальное исполнение

На этой стадии продукт силён именно как исполнитель системных действий, а не как полноценный социальный персонаж с памятью, эмоциями и длинным диалогом.

## 2. Рассматриваемые варианты

| Вариант | Плюсы | Риски | Вывод |
| --- | --- | --- | --- |
| Pixel-only | быстро, дёшево, просто | слабое ощущение живого ассистента | подходит для MVP, но ограничен по выразительности |
| Live2D | максимальная плавность и эмоции | сложный pipeline, риггинг, лишняя стоимость | рационален только на более зрелой стадии |
| Гибридный 2D state-driven | контроль, простота, хорошие UX-сигналы | выразительность ниже, чем у Live2D | лучший баланс для текущего проекта |

## 3. Рекомендация

Для WavyOS сейчас наиболее предпочтителен гибридный state-driven 2D-аватар, а не полноценный Live2D.

Практически это означает:

- отдельные состояния: `idle`, `listening`, `thinking`, `speaking`, `executing`, `error`
- простые анимации и/или спрайты
- реакции на системные события
- базовый lip sync по уровню громкости

Такой вариант усиливает UX уже сейчас, не ломает архитектуру и не требует тяжёлого production-пайплайна.

## 4. Почему это решение лучше именно сейчас

- оно соответствует текущей зрелости продукта: у системы уже есть команды и сценарии исполнения, но ещё нет полноценной личности, памяти и planner-слоя
- оно снижает технический риск: не нужен Live2D rigging, сложный runtime и дорогая подготовка ассетов
- оно даёт полезный UX-эффект уже в MVP: пользователь видит состояние ассистента и лучше понимает, что происходит
- оно не закрывает дорогу в будущее: state machine и `AvatarController` можно позже подключить к Live2D без смены общей логики

## 5. Что брать в ближайший спринт

- сформулировать state machine аватара и события переходов
- реализовать `AvatarController` и `Renderer` независимо от STT и command layer
- сделать минимальный набор визуальных состояний и простейший lip sync
- отложить Live2D до момента, когда появятся память, эмоции, длительные диалоги и подтверждённая продуктовая ценность персонажа

## Итог

Сначала — управляемый и понятный UX-слой, потом — сложная живость.
